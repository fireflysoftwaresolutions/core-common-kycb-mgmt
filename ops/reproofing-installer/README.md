# Credential-loss recovery authority installer

This optional installer is independent of Flyway. Never run it automatically against a retained database. The application stays disabled unless all explicit trust, workload and provider-policy configuration is present. No real provider or production activation has been accepted.

An installer administrator creates a non-login `reproofing_owner` and a separate login `reproofing_runtime`, grants the owner schema creation rights, then runs:

```sh
psql -X -v ON_ERROR_STOP=1 -v reproofing_owner=reproofing_owner -v reproofing_runtime=reproofing_runtime -f ops/reproofing-installer/install.sql
```

Use a new qualified schema/database and an approved installer identity. The runtime gets SELECT/INSERT/UPDATE on case and budget tables and SELECT/INSERT on the append-only audit table; it gets no DELETE, DDL or audit UPDATE. The installer deliberately fails if tables already exist instead of overwriting or resetting retained authority.

Set `firefly.reproofing.enabled=true` only for a qualified deployment. Configure `firefly.reproofing.issuer`, `realm`, `tenant`, `provider-id`, `policy-id`, `receiver.client-id`, `receiver.secret-file`, `native.base-url`, `native.client-id`, `native.secret-file`, `evidence.base-url`, `evidence.client-id`, and `evidence.secret-file`. Secrets are mounted files of 32 to 2048 characters, with no committed default. Native URL ends in `/firefly-recovery/lost-credentials/rpc`; evidence URL is the exact Domain `/internal/identity-recovery/evidence` endpoint. Use distinct identities and credentials for each direction. Outbound calls require HTTPS with ordinary certificate/hostname verification, reject redirects, time out after five seconds, and bound responses to 32 KiB. The receiver requires HTTPS and exact Basic identity for its explicit POST operations. Configure the real TLS listener and approved truststore; do not trust caller-supplied forwarding headers. Request bodies are bounded to 32 KiB.

The standalone executable is `core-common-kycb-mgmt-web/target/core-common-kycb-mgmt.jar`. Existing application database configuration uses `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_SSL_MODE`, `DB_USERNAME`, and `DB_PASSWORD`; the reproofing runtime role must have the approved existing-service privileges separately. This installer does not alter existing tables. Hosted fixtures may disable Flyway on an empty authority-only database; that is not retained-database rollout acceptance.

Cases preserve their original 600-second maximum expiry, binding and provider-start UUID. Domain must pass that UUID to the provider as its genuine idempotency key and refuse ambiguous starts if the provider cannot reconcile them. Confirm reservations last 15 seconds, exceeding bounded sequential verifier/admission RPCs. A crashed confirmation can be reconciled after that reservation expires without opening a new provider session. Outages release reservations without charging a failure. Authenticated rejected results consume only the three-opportunity case budget. Incomplete document, liveness, fraud or reference checks never charge a victim's subject ledger.

The durable subject/epoch ledger permits three fully verified grant issuances across all cases. Only a complete authenticated exact-reference proof and current native admission can charge `identity_reproofing_budget.verified_grants`. Retrying a finalized case preserves its grant without another charge. Only native canonical credential transition advances the stable epoch; starting a new ceremony cannot reset it. No counts are exposed to a browser. Deployment still requires approved source-abuse and escalation policy.

`identity_reproofing_case` holds durable cases, provider reservations/session, evidence reference/digest, canonical authorization/execution and original expiries. `identity_reproofing_audit` records transitions once, including confirmation-specific failed outcomes. `identity_reproofing_budget` stores the verified-grant ledger keyed by a length-prefixed SHA-256 of issuer/subject/epoch. Evidence IDs are unique per provider across cases. Native journal RPC is independently authenticated and checked before recording execution. An exact journal committed within the original grant validity can reconcile after expiry; it cannot create a grant, consume again or authorize another native mutation.

No HTTP call executes under a Core row lock. A native state change between admission and consumption is finally refused under the native user/state lock. Raw evidence, biometrics, documents, passwords and enrollment secrets do not belong in these tables or service logs. Never enable SQL bind-value or HTTP body logging for recovery traffic. Real proofing acceptance, notifications, source-abuse rules, retained-data rollout, workforce authority and immediate old-JWT rejection at every receiving service remain separate external gates.
